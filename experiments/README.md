## 2. 每类文件说明什么

E1 单轮目录通常采用 `<批次>-P场景-vu并发数-r重复序号` 命名。E2 按部署阶段和副本轮次组织。不同场景按需要保存下列文件。

| 文件 | 用途 |
| --- | --- |
| `matrix.json`、`manifest.json` | 批次计划、实际完成情况、代码提交和起止时间 |
| `workload.json` | 本轮场景、并发、重复序号、预热与测量窗口、上传上限、冷却结果 |
| `requests.csv` | 逐次 HTTP 请求的阶段、时间、延迟、状态、成功标记、错误分类和正文字节数 |
| `iterations.csv` | 业务迭代记录；分享的一次迭代通常包含验证和下载两次 HTTP 请求 |
| `errors.csv` | 失败明细；结合 `requests.csv` 判断正式窗口内的失败数量 |
| `resources.csv`、`load-generator.csv` | 服务资源、负载工具和宿主监测数据，保留真实采样时间戳 |
| `collector.json`、`collector-output.log` | 采集方式、间隔、异常及采集器标准输出/错误 |
| `execution.log` | 预热、正式测量、冷却等阶段的执行过程 |
| `environment.json`、`compose.redacted.json`、`configuration.redacted.json` | 硬件、版本、镜像、程序哈希和脱敏配置 |
| `checksum.json`、`cleanup.json` | 文件 SHA-256 校验、上传对象清理及配额恢复证据 |
| `downstream.csv`、`application.log` | 下游调用耗时和应用日志，按场景提供 |
| `smoke.json`、`smoke.log` | 业务冒烟检查的逐项结果与执行输出 |
| `metrics.json`、`aggregate.csv`、`per-round.csv`、`figures/` | 从原始记录计算的指标、重复汇总和图表 |

E2 还保存 `timing.json`、`startup-observations.json`、容器/网络/卷快照、`up.log` 和版本切换记录，用于判断部署何时可用、更新了哪些服务。各阶段名称与解释见 E2 报告。

统计性能时，按 `workload.json` 中的正式窗口和 CSV 的 `phase` 区分预热、测量与收尾。登录、文件校验和清理记录用于验证执行条件，不能直接加入业务性能样本。三次重复的中位数与范围、成功吞吐、晚完成请求等口径以报告和分析脚本为准。

## 3. 补充日志归档

2026 年 11 月 16 日合并主分支时，对原有实验记录做了完整性核对，并补充本机日志。该次归档索引了提交 `3246a73` 中的 1,698 个实验文件，另收录 55 份日志和诊断记录，约 39.57 MiB：42 份日志、11 份 JSON、2 份 CSV。这里的数量对应那次归档范围。

补充内容包括原生四个批次各六服务的 24 份日志、WSL 内三份 Nginx 文件日志、初次启动诊断、API 验收记录，以及原六容器当时仍保留的日志。8 份空日志也保留；文件为空表示该输出渠道没有内容，具体采集状态结合批次记录判断。

原文留在本机，公开副本对密码、JWT、提取码、分享访问令牌和内部凭证做脱敏，并统一为 UTF-8/LF、清理行尾空白。公开副本的 SHA-256 应与 `archived_sha256` 比较；`source_sha256` 对应本机原文。两者因脱敏和格式归一而可能不同。Git blob 标识对应仓库中的标准字节，不受 Windows 检出时的换行转换影响。

## 4. 时间和覆盖范围

原始时间字段通常使用 UTC，报告使用北京时间（UTC+8）。核对跨文件事件时先统一时区，再按正式窗口截取。

六容器补充快照截至北京时间 **2026-11-16 22:05:02**，即清单中的 UTC `2026-11-16T14:05:02.800653+00:00`。这类日志横跨启动、实验和恢复后的活动，要结合轮次时间与请求标识定位。原生 Nginx 文件日志累计覆盖多个原生批次，其 access 日志源格式不含时间戳，归档保留了这一格式。

容器快照包含采集时仍保留的日志。已经移除的容器或已被轮转丢弃、此前没有保存的内容无法恢复；E2 已移除测试容器的证据以 `E2/20261116-e2-formal/` 中先前保存的阶段日志为准。试跑、失败、中断和暂停记录用于解释准备过程，与正式结果分开引用。

私有凭证文件、镜像包、VHDX、编译缓存和数据库数据文件保存在相应本机环境中，不属于此处的公开实验日志。

## 5. 后续写论文与补充记录

引用某项结论时，先从报告找到批次和场景，再查完成清单、轮次参数、原始请求与资源数据；需要解释错误或部署过程时，再关联同时间段的服务日志。记录实验提交、场景、并发、重复次数和统计口径，便于他人复核。

调整程序、配置或负载后使用新的批次目录，保留旧批次及其失败记录。新增原始数据、执行日志、环境快照和校验结果一起提交，再更新报告与索引。日志归档使用全新名称，不覆盖已有快照；工具与命令见[部署工具说明](../scripts/deployment/README.md)。
