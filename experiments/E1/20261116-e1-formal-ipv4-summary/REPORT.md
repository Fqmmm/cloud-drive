# E1 阶段报告：P1—P3

2026-11-16 14:23（北京时间）完成 P1—P3 共 27 轮，按用户要求暂停。全计划含 20 MiB 扩展共 42 轮；P4、P5U、P5D 的 15 轮尚未测量。本报告只汇总已完成的正式窗口。

## 环境与方法

- 测试代码冻结提交：`5fb0392cbf0e71ec8c8f7ce4d42d0ba46c8a4d72`，分支 `feat/e1-performance`。应用镜像未在测量中重建；版本、镜像摘要和脚本哈希见 [environment.json](environment.json)。
- Windows 11、Intel Core Ultra 9 285H、16 个逻辑处理器、约 31.50 GiB 主机内存。Docker Desktop/WSL2 分配 4 CPU、4,107,522,048 字节内存；MySQL 与 MinIO 使用命名卷。Docker 29.9.2、Compose 5.6.1。
- Windows 主机运行 Python 3.13.5/requests 2.32.4 闭环负载，访问 `http://127.0.0.1:8080`，经过同一 Nginx 入口。独立进程通过 Docker Engine API 约每秒采集六个容器；psutil 同时记录压测进程和主机资源。
- 每个场景使用 5、10、20 VU，各重复三次，并轮换并发顺序；每轮预热 30 秒、正式 120 秒、冷却至少 30 秒。每次业务迭代后思考 1 秒。各 VU 使用独立账号、目录和数据，列表目录有 100 条记录；登录与数据准备在正式窗口外完成。
- P1 为列表；P2 为 1 MiB 上传；P3 为 1 MiB 下载。P2 每 VU 含预热最多 150 次上传，各轮均未触及上限。轮间清理发生在正式窗口外。
- 请求延迟统计含失败请求；成功 RPS 仅计正式窗口内完成的成功请求。正式窗口内发起、窗口后完成的请求保留在成功率中，共有 8 次成功晚完成。下表的 RPS、P95、P99 均为三轮指标的中位数，方括号为最小值—最大值；P95 中位数不是合并所有请求后的 P95。

共 **630 次轮前/轮后种子文件 SHA-256 校验全部一致**。P2 共清理 14,635 个上传文件（含预热），各轮作用域内对象剩余为 0，配额均恢复。对象删除与后台清理存在竞争，部分 `mc rm` 返回非零；清理成功依据是后续对象枚举与配额复核。用于后续 P4/P5 的种子、分享和本地私有凭证仍保留。

CPU 100% 表示占用一个 Docker 逻辑核，四核总上限为 400%；内存按 usage 减 inactive_file 的工作集口径统计。表中是各容器分别出现的峰值，不能相加作为同一时刻总峰值。各轮容器 CPU/内存均值与峰值见 [resource-summary.csv](resource-summary.csv)。

正式窗口预期采样 19,440 条，实际 19,425 条，缺失 15 条（0.0772%），已获取样本的 CPU 字段完整。独立采集器全程累计 22 次 OSError，正式窗口缺失按服务为 auth/file/frontend 各 2 条、minio/mysql/share 各 3 条。各轮各服务平均采样间隔约 1.000—1.011 秒，全程最大间隔 2.012 秒。缺口保留在原始记录和逐轮采集说明中，未用零值填补。

压测进程 CPU 单轮均值最高 16.28%、瞬时峰值 26.5%（100% 为一个主机逻辑核），RSS 峰值约 54.07 MiB；主机 CPU 单轮均值范围 12.50%—21.27%。全部轮次冷却稳定检查通过。固定 1 秒思考时间限制了闭环模型的请求到达率，因此这些数据描述当前负载下表现，不能据此推算最大吞吐容量。

P1 的 P95 在三档并发下约 7.5 ms；P3 约 21—24 ms；P2 约 91—103 ms，且 P99 随并发从约 220 ms 增至 378 ms。前三个场景中上传的尾部延迟更高，未观察到容器 CPU 饱和；下载的短暂 503 仍需后续诊断。P4 尚未测量，暂不判断完整系统的瓶颈。
