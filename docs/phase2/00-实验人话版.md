这四组实验是在从四个角度检查同一个网盘：

| 实验 | 要回答的问题 |
|---|---|
| 性能实验 | 人多了以后，网盘还能不能顺畅使用？ |
| 编排与部署实验 | 能不能一次启动整个系统，并单独更新其中一个服务？ |
| 故障恢复实验 | 某个服务坏了，哪些功能受影响，多久能恢复？ |
| 持久化实验 | 容器删掉重建后，用户和文件还在不在？ |

下面分别说清楚实际要做什么。

**第一组：性能实验，就是让一群“模拟用户”同时使用网盘。**

先启动完整系统，再用测试工具模拟 5 人、10 人、20 人同时操作。工具会反复执行文件列表查询、上传、下载和分享访问，每种操作分别测量。

例如，先让 5 个模拟用户不断上传文件，记录两分钟；再换成 10 人、20 人，用同样的文件大小、同样的操作方式测试。每种情况重复三次，减少偶然结果的影响。

主要看四件事：

- 请求有多少成功、多少失败。
- 每秒能完成多少次操作。
- 用户通常要等多久，比较慢的请求要等多久。
- 各个容器用了多少 CPU 和内存。

其中，**P95 响应时间**可以理解为：100 次请求中，大约有 95 次能在这个时间内完成。例如 P95 为 800 毫秒，表示绝大多数请求能在 800 毫秒内完成。

这组最后要拿出数据和图表，说清楚“人数从 5 增加到 20 后，哪个操作明显变慢，系统哪里开始吃力”。不需要证明微服务一定更快，测到什么就分析什么。

**第二组：编排与部署实验，就是检查“整套系统怎么启动、怎么更新”。**

它分成两个主要部分。

第一部分是**一键启动**。在准备好的测试环境中执行启动命令，让前端、三个后端、MySQL 和 MinIO 六个容器一起启动。然后实际完成登录、上传、下载和分享，确认整个系统能用。

计时要一直记到业务操作成功。六个容器显示“正在运行”，还不足以证明网盘已经可以使用，因为数据库可能仍在初始化。

第二部分是**单独更新一个服务**。例如把分享服务的版本从 v1 更新到 v2，同时持续检查登录和个人文件功能。更新之后，要证明：

- 分享服务确实换成了新版本。
- 其他五个容器没有跟着重建。
- 原来的分享链接仍然可用。
- 更新期间哪些功能短暂受影响，影响了多久。

这组最后要展示：**Compose 能统一启动六个容器，也能单独更新其中一个。**

如果做扩展，可以让分享服务运行两个副本，再证明请求确实分到了两个副本。目前这部分不属于基础必做。

**第三组：故障恢复实验，就是有计划地让系统的一部分“坏掉”，观察后果。**

每次只制造一种故障，例如：

| 制造的故障 | 实际检查什么 |
|---|---|
| 停止分享服务 | 分享打不开时，登录和个人上传下载是否仍能用 |
| 停止认证服务 | 新用户无法登录时，已经登录且凭证有效的用户是否还能操作文件 |
| 停止文件服务 | 登录是否还能用，文件和分享下载如何报错 |
| 停止 MinIO | 文件列表是否还能显示，上传下载是否失败 |
| 让分享服务的 Java 进程异常退出 | Docker 是否自动重启它，业务多久恢复 |

测试脚本会持续发请求，把故障前、故障中、恢复后的结果记录下来。

这里要区分两种恢复：

- **人为停服**：人为停止服务，等待 30 秒，再人为启动。观察的是停服影响和启动后的恢复。
- **程序异常退出**：让程序自己异常终止，观察配置好的重启策略是否自动把它拉起来。

不能用“我手动启动成功了”证明系统具备自动恢复能力。

这组最后要拿出一张清楚的影响表和时间记录，说明：**坏了哪一部分、哪些功能还活着、哪些功能失败、怎么恢复、用了多久。**

**第四组：持久化实验，就是检查“容器换了，数据是否还在”。**

先创建测试用户、目录和文件，再创建分享链接。然后分别重建 MySQL 容器和 MinIO 容器，**保留它们使用的数据卷**。

可以把容器理解为运行程序的环境，把数据卷理解为单独存放数据的地方。这组实验要验证：换一个容器继续使用同一个数据卷，能不能接着使用原来的数据。

MySQL 重建后，检查：

- 原用户能否登录。
- 目录和文件记录是否还在。
- 配额和分享记录是否正确。

MinIO 重建后，检查：

- 原文件能否实际下载。
- 原分享能否继续下载文件。
- 下载内容是否与上传前完全一致。

最后一点通过 **SHA-256 校验值**判断。它相当于根据文件内容计算出的指纹：重建前后的文件指纹相同，就能支持“内容没有变化”的判断。仅看到文件名还在，不能证明文件内容完整。

这组按固定步骤重启应用、恢复访问后再检查数据，重点验证的是**数据有没有保住**；自动恢复速度由第三组负责。
