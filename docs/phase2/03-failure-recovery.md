# 实验三：服务故障影响与恢复

负责人：刘骐语。关联：[总体方案](../plan.md)、[分享服务](../phase1/share-service.md)。

## 1. 要验证的行为

测量单服务不可用对不同业务的影响，验证本地 JWT 认证带来的调用边界，并区分人工停服、应用进程异常退出与依赖中断的恢复方式。六容器使用同一台宿主机，本实验观察进程和服务级恢复。

共享 MySQL 是共同依赖。停止数据库时三个业务服务都可能受影响，报告按实际范围记录。前端页面能打开与后台业务能成功分别统计。

## 2. 持续探测和基线

准备两个用户、一份源文件、一个有效公开分享、一个带提取码分享及其 SHA-256。每个故障轮次在注入前取得 JWT，记录到期时间，确认剩余有效期覆盖该轮预热、故障窗口和恢复；同一轮内使用同一令牌。停止 auth-service 的轮次保留该轮注入前取得的 JWT，不依赖停服期间重新登录为私有请求补发凭证；登录探针仍按原计划验证新登录的可用性。

刘骐语 编写每秒一次的并行探测：登录、带 JWT 的个人文件列表、个人下载、分享校验和匿名下载。每条请求设置上限；普通查询 5 秒，下载 15 秒。探测之间独立，单个超时不阻塞整轮调度。记录计划时间、实际发出时间、返回时间、HTTP 状态、业务码、结果类别和耗时。

故障前稳定探测 30 秒，记录容器 ID、StartedAt、RestartCount、健康状态与就绪状态。先确认所有探测成功，下载校验值一致。

## 3. 故障矩阵

| 编号 | 操作 | 重点业务与预期 |
|---|---|---|
| F1 | 人工停止 share-service 30 秒 | 登录、个人列表及下载继续；分享失败 |
| F2 | 人工停止 auth-service 30 秒 | 新登录失败；已有有效 JWT 的个人文件及分享管理继续 |
| F3 | 人工停止 file-service 30 秒 | 登录继续；文件业务与实际分享访问失败；本人分享列表可读取快照 |
| F4 | 人工停止 minio 30 秒 | 登录与列表继续；上传、个人下载和分享下载失败 |
| F5 | 让 share-service 的 Java 主进程异常退出 | 观察容器自动重启、重启计数与业务恢复 |
| F6 扩展 | 人工停止 mysql 30 秒 | 记录公共依赖故障范围及连接恢复 |

停止服务用 `docker compose stop <service>`，30 秒后执行 `docker compose start <service>`。人工停止场景单独记录人工恢复时刻。每次只注入一种故障，恢复后连续三次探测成功再开始下一轮。F1—F5 每类重复三次。

每轮 MinIO 故障前单独创建一份待删除文件，不使用其他实验的基线样本。中断期间额外发起一次上传和删除：上传失败不增加配额；删除逻辑失效后形成的待清理任务，在 MinIO 恢复后完成。故障恢复后抽查文件完整性和配额。

## 4. 主进程异常退出的可复现方法

肖国扬 在分享服务提供仅用于实验的故障钩子：`POST /internal/test/exit`，由 `EXPERIMENT_FAULTS_ENABLED=true` 显式启用，校验内部凭证。默认关闭且前端入口不转发。钩子写入请求 ID和时间后，使 JVM 以约定非零码退出，例如 `Runtime.halt(17)`；请求连接中断属于预期现象。

刘骐语 通过容器网络中的受控工具调用钩子，工具作为宿主机脚本或一次性工具容器运行，记录退出码和日志。基础业务容器仍为六个。Dockerfile 采用 exec 启动 Java，先确认 PID 1 为 JVM。分享服务成功运行至少 10 秒后再注入故障，并保留调用前后的 RestartCount、FinishedAt、StartedAt 和日志证据。

容器使用 `restart: unless-stopped`，观察异常退出后的自动恢复。人工执行 stop 与应用自行退出分开测试，健康检查失败也单独记录。[Docker 重启策略](https://docs.docker.com/engine/containers/start-containers-automatically/)、[Compose 健康检查与重启配置](https://docs.docker.com/reference/compose-file/services/)

阶段一联调由 肖国扬、刘骐语 验证该钩子；实验结束关闭环境开关并确认路由不可用。故障钩子不接受任意命令、不读写业务数据，认证凭证不写日志。

## 5. 恢复时间和影响计算

时间线至少包含：t0 发起注入、t1 首次业务失败、t2 进程退出/服务确认停止、t3 人工启动指令（仅停服场景）、t4 新进程启动、t5 连续三次成功中的第一次成功。

- 自动恢复耗时：F5 的 t5−t0，同时报告从退出到新进程启动、到业务可用的分段时间。
- 人工启动后的恢复耗时：t5−t3；30 秒停服窗口另列。
- 业务失败窗口：首次失败到稳定恢复的时间，探测间隔带来约 1 秒量级的检测分辨率，实际超时和调度偏差另记。
- 影响范围：每条业务在故障窗口的成功率和错误分布。

容器显示 running、健康探测通过、完整业务恢复分别记录。Nginx 因重建 IP 变化需 reload 时，将该操作及耗时计入恢复过程；同容器重启与重建分开标记。

## 6. 原始数据、报告和收尾

每轮保存到 `experiments/E3/<run-id>/`：probe.csv、事件时间线、容器状态快照、脱敏日志、校验结果及故障命令。生成业务×故障影响表、故障时间线和恢复时间表，列出三次原始数值及中位数/范围。

验收要求故障可复现、人工与自动恢复行为区分清楚、依赖故障范围有证据、恢复后业务与文件完整。意外失败保存记录并排查，修复后另建批次。

收尾确认六容器恢复、故障开关关闭、探测全部通过、待清理任务处理完成，再把测试环境交给下一组实验。
