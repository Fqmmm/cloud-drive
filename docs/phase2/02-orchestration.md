# 实验二：Compose 编排与独立部署

负责人：范骐鸣。关联：[总体方案](../plan.md)、[前端](../phase1/frontend.md)、[分享服务](../phase1/share-service.md)。

## 1. 目标和范围

基础实验验证六容器能否从源码统一启动、依赖是否按就绪状态接入、单独更新分享服务是否保持其他容器运行。扩展实验验证分享服务两个副本的请求分发及性能变化。

基础架构为六个常驻容器，扩容分享服务后临时为七个。负载工具与一次性管理工具单独登记。实验在独立的课程测试项目中执行，项目名和卷名全程记录。

## 2. 阶段一准备工作

范骐鸣 汇总 `compose.yaml`、`.env.example`、启动与验证脚本。肖国扬、狄东琛 提供每个镜像的构建上下文、端口、环境变量、健康检查与启动命令。启动脚本执行配置检查、构建启动和业务探测，并以非零退出码报告失败。

部署手册写清 Docker/Compose 版本、资源需求、镜像来源、环境文件设置和执行目录。首次部署由文件服务创建私有桶，MySQL 自动初始化三库。数据库和 MinIO 使用命名卷，应用通过服务名寻址。

使用 `depends_on: condition: service_healthy` 等待依赖就绪，健康检查命令在实际镜像中验证。[Docker 启动顺序](https://docs.docker.com/compose/how-tos/startup-order/)

应用镜像包含或提供能执行健康检查的工具；就绪接口设置有限超时。Nginx 重建后的域名解析和 reload 步骤纳入更新脚本。日志、截图和配置输出过滤真实凭证。

## 3. 基础实验 A：一键部署

建议命令在仓库根目录执行，环境文件已配置：

```powershell
docker compose config --quiet
docker compose up -d --build
docker compose ps
docker compose logs --since 5m
```

计时终点使用完整冒烟流程首次通过的时刻，不能只取 `up -d` 命令返回。另记所有容器就绪时刻，区分“进程启动”“依赖就绪”和“业务可用”。

记录两类环境：

- 首次部署：记录镜像/依赖缓存、是否需要下载、初始空卷及实际拉取构建耗时；至少完成一次。
- 已有镜像启动：先完成构建，固定镜像、项目名、环境和数据卷。每轮执行下列命令，重复三次；从 `up -d` 开始计时到冒烟通过，关闭和清理时间单独记录。

```powershell
docker compose down
docker compose up -d
```

`down` 保留命名数据卷，每轮不加 `-v`。冒烟脚本使用唯一测试账号或可重复执行的数据准备，避免已有数据造成伪失败。已有卷启动不计为首次初始化。缓存构建耗时若需要比较，单独执行和记录 build 阶段；对已经运行且无变更的系统执行一次 up 不作为启动实验。

首次部署如需另建空卷，使用新的实验项目名并检查实际卷名，不删除已有业务卷。缓存状态和数据状态分别描述。部署完成后验证注册、上传、下载、创建分享和匿名下载，保存六服务状态、网络成员和数据卷挂载清单。

## 4. 基础实验 B：单服务更新

1. 保存六个容器的 ID、StartedAt、镜像 ID 和 APP_VERSION，持续探测登录、文件列表与有效分享。
2. 肖国扬 将分享服务 APP_VERSION 从 v1 改为 v2，并完成对应源码或构建参数调整。
3. 执行独立构建与更新：

```powershell
docker compose build share-service
docker compose up -d --no-deps share-service
```

4. 检查更新后的 IP 解析，按基础配置显式 reload frontend 的 Nginx；reload 命令使用已交付脚本。
5. 验证分享响应头显示新版本、原分享仍可使用，登录与个人文件探测继续通过。
6. 对照更新前后容器 ID 和启动时间，确认 frontend、auth-service、file-service、mysql、minio 没有重建。Nginx reload 不改变容器 ID。

记录分享服务不可用窗口、其他业务失败数、构建与更新耗时。采用单副本替换时，分享短暂不可用按实记录；实验展示独立更新及影响范围。

## 5. 扩展实验：分享服务双副本

前提是基础验收通过、share-service 不依赖实例内必要会话、无冲突后台任务，并已提供 X-Instance-Id。数据库共享，三服务 JWT 和内部凭证保持一致。文件服务维持单副本。

扩容服务不设置固定 container_name，不发布固定宿主机端口。Nginx 使用经验证的上游配置发现两个地址，扩容后 reload 并检查解析结果；也可使用经过版本验证的动态发现配置。[Compose 服务定义](https://docs.docker.com/reference/compose-file/services/)

```powershell
docker compose up -d --no-deps --scale share-service=2 share-service
```

连续请求至少 100 次，记录响应实例标识与每实例请求数，确认两个实例都收到业务请求。验证跨实例创建、访问和取消分享的一致性。每实例提取码限流单独记录，不推导为全局限流。

从实验一选定一个使单副本负载明显上升且错误可控的固定并发，分别在一副本与两副本下预热 30 秒、测量 120 秒、重复三次。记录总资源预算：基础对比保留相同机器资源；若第二副本增加应用总额度，将其列为“增加资源后的扩容效果”。数据共享或文件服务成为瓶颈时，结果可表现为提升有限。

完成后恢复单副本并 reload Nginx：

```powershell
docker compose up -d --no-deps --scale share-service=1 share-service
```

再次执行冒烟验证。手动扩容调整的是单机副本数量，报告中使用“手动扩容”和“请求分发”描述结果。

## 6. 记录、交付与验收

每轮保存到 `experiments/E2/<run-id>/`：环境及缓存状态、部署时间线、容器快照、网络/卷清单、探测记录、构建日志、更新前后版本。扩容部分另存实例分发 CSV 和性能原始结果。

基础验收要求六容器自动初始化并可用；分享能单独更新；其他容器保持运行；原有数据和分享继续可访问。扩展验收增加两实例分发证据、跨实例一致性和前后测量结果。交付 Compose、环境模板、部署/更新/恢复脚本、实验数据和报告。
