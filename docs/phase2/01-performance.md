# 实验一：核心业务性能与资源开销

负责人：范骐鸣。关联：[总体方案](../plan.md)、[文件服务](../phase1/file-service.md)、[编排实验](02-orchestration.md)。

## 1. 实验问题

测量六容器系统在不同并发下的请求成功率、吞吐量、响应延迟和资源占用，找出首先出现排队或错误的业务。基础实验比较同一系统的三档负载，输出结果只对应记录的硬件、数据量和配置。

按组长 2026-11-16 的安排，增加同一六服务应用的容器与非容器部署对照，非容器侧在 WSL2 中直接运行服务进程。复用相同 JAR、前端产物、软件版本及负载参数，维持 4 CPU、配置内存 4 GiB；记录实际可用内存、JVM 参数、网络路径和存储位置。C/D 分区同属物理磁盘 0，当前两侧 VHDX 位置不同，结果解释为两种已记录部署条件的对照。P5 本轮不考虑，保留既有扩展记录。

## 2. 环境和数据准备

冻结源码提交与镜像标识，保存脱敏后的 Compose 配置、镜像 digest、Docker/Compose 版本、CPU 型号、宿主内存、Docker 可用 CPU/内存、操作系统及存储位置。Windows 环境注明使用 WSL2 文件系统还是宿主机挂载。负载工具运行位置及其资源占用也需记录。

使用 k6 或能输出等价指标的工具。脚本、工具版本和依赖在阶段一固定。每个虚拟用户使用独立账号或独立数据区，每个“场景×并发×重复”轮次在预热前重新登录，检查新 JWT 的剩余有效期足够覆盖预热、正式窗口和收尾。登录不计入测量，正式窗口内不刷新凭证，避免认证耗时或过期错误混入文件性能。无需为了整套矩阵统一延长产品默认有效期。

测试数据基线：每用户预置 100 条列表记录；上传和下载使用 1 MiB 文件，扩展实验另用 20 MiB 文件做大文件场景；文件内容可由固定随机种子生成，上传请求生成不同内容或唯一对象。累计上传量提前核算，保证剩余配额足够。所有分享在测量期间有效，受保护分享的提取码通过脚本安全注入。

## 3. 工作负载矩阵

| 场景 | 请求 | 数据与校验 |
|---|---|---|
| P1 列表 | GET 文件列表 | 固定目录；校验成功码、列表结构及预置条目 |
| P2 上传 | POST multipart 文件 | 1 MiB；校验返回文件 ID，按轮次清理 |
| P3 下载 | GET 个人文件下载 | 固定 1 MiB 文件；检查 HTTP 状态和长度，轮次前后做 SHA-256 |
| P4 分享访问 | POST 匿名分享校验并下载 | 校验与下载分别打标签；检查业务码、长度及校验值 |
| P5 大文件（扩展） | 单独上传/下载 20 MiB | 同样记录时间和字节吞吐，避免和 1 MiB 混算 |

基础矩阵为 P1—P4 × 5/10/20 VU × 3 次重复。P5 不影响基础验收，完成 P1—P4 且核算磁盘与配额后，先用 5 VU 并设置最大上传次数，再决定是否增加档位。每个 VU 发出一次业务请求后等待 1 秒，记录使用封闭负载模型；同一场景三档采用相同的等待策略。P4 一次迭代包含两次 HTTP 请求，区分请求吞吐与业务迭代吞吐。

每轮预热 30 秒，正式测量 120 秒，冷却至少 30 秒并等待资源回到稳定水平。正式统计单独标记时间窗口，排除预热和清理。上传下载慢到超时的请求仍计入失败，保存其错误类型。

## 4. 执行顺序

1. 运行 刘骐语 的冒烟脚本，确认六容器就绪及测试文件完整。
2. 保存环境快照，记录空闲资源，预生成账号、JWT、目录和分享。
3. 按矩阵执行场景；不同重复轮次轮换低、中、高档顺序，记录实际顺序。
4. 使用独立采集进程记录各容器 CPU 和内存，目标采样间隔为 1 秒，保存实际时间戳、丢失样本与采集工具版本；负载工具同步输出逐场景指标。范骐鸣 在试跑时确定 docker stats 等工具的采集与解析方式。网络、磁盘 I/O 在环境能稳定提供相应字段时附加采集，缺失字段标记为不可得。
5. 每轮检查下载样本 SHA-256 和业务错误，清理本轮上传文件，等待对象清理完成并核对配额。
6. 三次重复完成后汇总。失败轮次保留原始记录；修复配置或代码后作为新批次重新运行。

测试期间暂停镜像构建、扩容、故障注入和数据卷重建。镜像拉取与应用启动时间属于实验二，不计入请求性能。

## 5. 指标计算与图表

| 指标 | 定义 |
|---|---|
| 成功率 | 同时满足 HTTP 与业务校验的请求数 / 请求总数 |
| 吞吐量 | 正式窗口内成功请求数 / 秒；另列成功业务迭代数 / 秒 |
| 延迟 | 每场景均值、P50、P95、P99，失败与超时数量单列 |
| 字节吞吐 | 成功上传或下载的正文总字节 / 秒 |
| CPU/内存 | 各容器均值、峰值，注明 Docker CPU 百分比口径和内存口径 |
| 错误 | 参数、鉴权、配额、依赖、超时等分类计数 |

每轮独立计算分位数，三次结果展示中位数和范围，保留每次原值；不将三轮 P95 的平均值命名为整体 P95。所有场景均列出已有请求总数，P99 作为辅助观察；样本较少时注明尾部估计的波动，主要依据成功率、吞吐量和 P95 分析，不从单轮 P99 推导结论。保持每轮 120 秒与三次重复，不为 P99 另延长测试或增加轮次。

建议输出并发与成功吞吐、并发与 P95、各容器内存峰值三张主图。将错误率和字节吞吐附在结果表。观察到延迟上升后，用资源曲线、下游耗时和日志判断原因；证据不足时写明待验证的原因。

## 6. 原始记录与交付

每轮保存到 `experiments/E1/<run-id>/`：environment.json、脱敏配置、workload.json、负载原始输出、resources.csv、errors.csv、checksum.json 和执行日志。汇总表至少包含：场景、VU、文件大小、轮次、请求数、成功率、RPS、P95/P99、文件服务 CPU/内存峰值。

交付负载脚本、数据准备与清理脚本、原始数据、绘图方法和实验报告。报告回答：三档负载分别发生什么，哪个操作首先变慢，资源或下游依赖提供了什么证据。

验收以矩阵完成、数据可复算、重复运行参数一致为准。测量到性能下降或高负载错误时，保留结果并解释条件；错误修复前后的数据分开成批。
