# 实验四：数据持久化与文件完整性

负责人：刘骐语。关联：[总体方案](../plan.md)、[MySQL](../phase1/mysql.md)、[MinIO](../phase1/minio.md)。

## 1. 问题与证据

验证 MySQL 和 MinIO 容器被替换后，命名数据卷是否继续保存业务记录和文件内容。数据库保存元数据，MinIO 保存实际文件，两部分均需核验。容器重建实验和新卷备份恢复实验分别出具结果。

实验使用专用项目和测试数据，所有操作先记录 Docker context、Compose 项目名、容器 ID、卷名及挂载目标。基础流程保留原卷，命令不包含 `down -v` 或卷删除。涉及新卷恢复的扩展流程使用另一个项目名，原数据保留。

## 2. 建立测试样本

创建用户 U1、U2，分别建立目录；上传 1 KiB、1 MiB、20 MiB 的不同文件，其中至少一个文件名含中文和空格。保存原始文件、字节数和 SHA-256。为每份样本分别创建一个公开分享和一个带提取码分享，有效期覆盖整个实验；记录每份文件与两种链接的对应关系。

生成基线清单：用户/账户 ID、目录 ID、文件 ID、父目录 ID、文件名、字节数、对象键、配额、分享 ID、有效期和状态。凭证与提取码单独保存在受控运行环境，不进入公开清单。

数据写入完成后停止其他实验写入，等待文件对象清理任务为空。通过前端或 API 下载全部样本并计算 SHA-256，确认基线本身正确。使用只读运维查询和对象管理工具生成元数据、对象清单，两份清单按文件 ID 与对象键关联。

## 3. 基础实验 A：重建 MySQL

保存 MySQL 容器 ID 和 mysql_data 的实际卷名，备份测试数据后执行：

```powershell
docker compose up -d --no-deps --force-recreate mysql
```

等待 MySQL 就绪，保存新的容器 ID 与挂载信息，确认容器 ID 已改变且卷名保持一致。初始化脚本在已有卷上不重复建库，升级脚本也不在此步骤重放。

本实验按固定恢复步骤重新启动三个业务应用，等待就绪后 reload Nginx，再验证数据。应用重连与数据完整性分开记录：

```powershell
docker compose restart auth-service file-service share-service
# 等待三个业务服务就绪后执行
docker compose exec -T frontend nginx -s reload
```

是否能自动重连可作为附加观察，不能用“尚未重连”直接判定数据丢失。人工重启的开始结束时间单列，不将本流程耗时当作自动恢复时间；自动恢复能力由实验三评估。

验证 U1、U2 能登录，目录、文件、配额和分享记录与清单一致，两个用户仍隔离。通过原分享下载样本并核验 SHA-256，记录上述应用重启、依赖就绪和 Nginx reload 的步骤及耗时。

保留记录的主键、归属、大小与状态作为比较字段，最后访问时间等易变字段单列。保存数据库记录数及关键记录导出，不能只以页面显示条数判定。

## 4. 基础实验 B：重建 MinIO

在实验 A 通过后保存 MinIO 容器 ID、minio_data 卷名与桶对象清单：

```powershell
docker compose up -d --no-deps --force-recreate minio
```

等待 MinIO 就绪，按实验 A 的固定步骤重启三个业务应用，待就绪后 reload Nginx。核实新容器继续挂载原卷，桶仍私有，对象键和字节数一致。以个人下载和匿名分享下载两种方式获取所有样本，逐个比较大小和 SHA-256。

检查 U2 无法下载 U1 私有文件、错误提取码仍被拒绝，确保持久化后权限关系也被保留。重复 A、B 各三次，不重新上传样本，保存每次新容器 ID 和校验结果。

基础实验 C 可补充一次全应用重建：保留所有卷执行 `docker compose up -d --force-recreate`，恢复 Nginx 路由后复验完整闭环。该步骤单独记录，避免与单基础设施重建结果混算。

## 5. 删除与一致性检查

选一份额外测试文件创建分享后永久删除。验证活动列表不再显示文件、配额只扣减一次、旧分享的新访问失败、对应对象最终清理。MinIO 故障下的待清理重试与实验三共用记录，注明批次和源码版本。

若基础版本启用了去重，再补充同内容两文件：删除第一份后第二份仍能下载且校验通过；最后一个引用删除后对象按设计清理。首版一文件一对象时执行普通删除用例即可，报告按实际存储模型解释。

## 6. 扩展：备份恢复到新卷

前提是 狄东琛 已提供数据库导出和对象复制工具，基础持久化验收通过，备份磁盘空间充足。

1. 暂停三个业务服务写入，等待进行中的上传和对象清理结束，记录一致性批次号。
2. 导出三个逻辑库及所需结构，复制私有桶对象并保存对象键、大小和 SHA-256 清单。备份工具版本与参数写入记录。
3. 使用不同 Compose 项目名创建空的 MySQL、MinIO 卷，按恢复流程初始化账号和目标库、导入 SQL、恢复对象和私有桶策略。
4. 使用独立前端端口（如 8081）运行恢复系统，JWT/内部凭证及存储配置按恢复环境注入。
5. 验证登录、文件目录、配额、原分享链接的 token 路径和下载校验。分享域名按新环境配置，业务记录中的 token 保持一致。
6. 分别记录备份耗时、恢复耗时、备份大小及校验结果，保留原项目作对照。

恢复测试同时包含数据库和对象存储，使用一致停写窗口的备份。账号权限、桶策略及必要配置随恢复步骤重建。

## 7. 结果文件与验收

保存到 `experiments/E4/<run-id>/`：环境快照、baseline.csv、每次重建前后容器/卷清单、数据库导出或查询结果、对象清单、下载校验结果、执行日志。清单至少包含文件 ID、对象键、原始/下载字节数、原始/下载 SHA-256 和通过状态。

报告用表格逐项列出重建前后结果，说明数据存放在哪个卷、哪个容器发生替换、是否需要人工恢复。SHA-256 相同支持内容完整性，业务查询与权限用例支持元数据及授权关系保留。

基础验收要求 MySQL、MinIO 各三次保留卷重建后，记录可用、全部样本校验一致、原分享有效且权限隔离正确。备份恢复作为独立扩展结论。收尾恢复六容器正常运行，备份与测试文件按批次归档。
