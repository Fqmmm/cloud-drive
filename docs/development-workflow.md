# A 开发与 A、B 联调工作规范

版本 V1.1，2026-11-15。依据仓库 `dde9c6f` 整理，用户已接受工作规范及独立 Maven 工程建议，并要求按功能分别提交和推送。

## 1. 范围和依据

A 为肖国扬，负责 frontend、auth-service、share-service。B 为狄东琛，负责 file-service、MySQL 和 MinIO。本轮包含 A 开发、必要的 B 接口协调及双方开发自测。C、D 的整体编排和四组实验沿用既定分工。

业务范围以 `functional-requirements.md` 为准，职责和总体方案见 `plan.md`，接口和服务验收见 `phase1/`。本规范管理开发过程。规范不能自动修改已确认的功能、人员分工或架构。

发现文档与代码不一致时，记录差异、受影响调用方和处理建议，再落实修复或明确的文档调整。现有实现可以作为联调依据，不能仅凭实现宣称已经满足需求。

### 2.2 B 交付中可观察到的约定

B 没有单独的工作规范文件。以下来自 `backend/file-service/README.md`、`backend/sql/course-mysql/README.md` 和新增代码，属于已交付的工程约定。

- Java 17，文件服务独立 Maven 构建，源码构建镜像，Java 以 exec 形式启动。
- 配置由环境注入，数据库服务账号只访问自己的库，使用 UTC。

- 提供局部 Compose 用于独立联调，使用命名卷、健康检查、默认私有桶，并提供清理查询与操作说明。
- README 提供构建、启动和交接步骤。当前新增文件中没有独立自动化测试和运行验收记录，本轮阅读未验证实际运行结果。

B 的两个功能提交采用英文描述，未使用前端配置的 `type(scope)` 形式。历史提交予以保留，本轮新增提交采用下文约定。

## 4. Git 管理

1. 开始每轮先查看 `git status --short --branch`、近期提交和当前差异。历史课程基线为 `eef0ad1`，本轮接收 B 交付的阅读基线为 `dde9c6f`。
2. 实施阶段使用 `course/a-services` 或同类清楚命名的开发分支；先检查分支是否已存在。分支创建成功后才记录实际名称和起点。
3. 每个提交完成一个可审阅功能。按 `plan.md` 第 2.5 节拆分到注册、登录、文件浏览、文件操作、分享管理、匿名下载等功能；各服务的构建骨架可单独提交。对应验证、SQL 和文档随功能提交。
4. 提交消息采用 `type(scope): 描述`，例如 `feat(auth): implement personal account login`、`fix(frontend): preserve string file identifiers`、`docs(ab): record integration results`。
5. 使用明确文件路径暂存，提交前查看差异和 `git diff --cached --check`。确认未夹带他人改动、临时产物或真实凭证。
6. 业务变更和对应文档放在同一提交，较大的纯格式调整单独提交并说明必要性。
7. 用户已授权后续实施按功能提交和推送。每完成一个功能，验证、同步文档并审阅后，单独 commit 并 push 到开发分支，再开始下一功能。推送前检查待推送提交，避免积攒多个功能后批量推送，也不能把整个 A 的交付压成一个提交。真实依赖的先后功能可以逐次推送，不要求每个中间提交都完成整个产品流程。
8. 本轮新建的本机环境文件、构建产物、临时下载文件和工具缓存应被正确忽略。前端开始固定依赖时应提交 pnpm 锁文件，并同步移除现有忽略规则。
9. 推送失败时保留提交并记录原因，先排查和重试，再推进下一功能。重写共享历史、强推、删除分支和合并主分支需要具体授权。远端发生变化时先获取并检查差异，再安全整合，不覆盖他人提交。

## 5. 接口和数据库变更

- A、B 共用一份可查阅的 JWT 与 HTTP 协议。业务 ID 为字符串，根目录为 `"0"`，`isDirectory` 为布尔值，容量为 `totalBytes` 和 `usedBytes`。
- 成功 JSON 使用 `{code, msg, data}`，成功码为字符串 `00000`。HTTP 状态与业务码同时有效；下载成功返回二进制流，失败保留可识别的状态和错误信息。
- JWT 固定 HS256，密钥为至少 32 字节的 UTF-8 原始值。签发和校验 `sub`、`accountId`、`iat`、`exp`、`iss`、`aud`，默认有效期两小时，时钟偏差须明确一致。
- 内部调用携带 `X-Internal-Token`，分享服务从已核验分享记录取得 ownerId 和 fileId。浏览器提供的 userId 不作为操作授权依据。
- 接口变化先列出方法、路径、参数、响应、错误、调用方和兼容影响，再同步实现与文档。B 的接口发生问题时，先给出复现和影响，再进行最小修复。
- auth_db 和 share_db 初版 SQL 已由 B 提供，A 落地时核对字段与状态含义，尤其是账户状态、分享状态、提取码散列和时间字段。文件表由 B 维护。
- 只访问自身业务库，跨服务调用使用 HTTP。SQL 使用参数绑定。
- 全新部署更新初始化脚本；已有课程卷升级同时提供顺序明确的迁移 SQL、备份步骤和版本登记。仅修改初始化 SQL 不代表已有数据库已升级。
- 数据操作前确认 Docker context、项目名、数据库和卷。测试使用独立项目与样本，保留可用数据，清空数据库或删除卷须有针对该对象的明确授权。

## 6. 代码与配置

课程服务优先使用清楚、适量的 Controller、业务处理、数据访问和下游客户端边界。简单模型允许 Java record，SQL 允许 JdbcTemplate 参数化调用。拆类以职责和可读性为依据，避免单纯为行数或形式新增接口与转换层。

旧 MyBatis、MapStruct 和注解规则继续适用于原目录。新增课程服务不因旧工具限制强行引入整套旧依赖。文件、类、方法达到旧长度阈值时审查职责和复杂度，必要例外记录原因。

A 的依赖只包含当前业务需要的内容。HTTP 查询、文件传输、数据库访问使用有限超时；重试只用于适合安全重试的操作。下载采用流式处理，连接结束时释放资源。

新增代码解释权限边界、事务、补偿、重试和易错行为。接口参数与配置要有可查说明。提交课程成果时结合指南检查源码注释要求，避免用无意义注释凑比例。

配置文档说明名称、必填性、默认值、单位和使用方，示例使用占位值。密码、JWT、提取码、内部凭证和完整敏感请求不得进入仓库或日志。公开响应不返回私有存储地址和内部服务凭证。

Java 按 17 构建目标验证；Node 按 `frontend/package.json` 的 engines 要求选择并记录版本。镜像与依赖记录已验证版本，实际拉取后再登记 digest。

## 7. 检查方式和工具限制

| 范围 | 最低检查 | 说明 |
|---|---|---|
| 文档变更 | Git 空白检查、链接目标、命令路径及事实核对 | 本轮只增加文档时无需启动服务 |
| A 的新服务 | `mvn -f backend/auth-service/pom.xml verify` 或 share-service 对应命令 | 服务建立后执行；无测试时构建成功不等于业务已验证 |
| 相关前端 | 在 frontend 执行 `pnpm exec vue-tsc --noEmit`，成功后执行 `pnpm exec vite build` | 原 build 脚本使用 `&`，不能只凭最终退出码认定两个步骤均成功 |
| 前端静态规范 | 对改动文件运行 ESLint、Prettier、Stylelint 的检查模式 | 避免直接运行会批量 `--fix` 的全项目 lint 脚本 |
| 原后端改动 | 在 backend 执行 `python script/code_check.py . --mode incremental --base <实际基线>` | 默认配置为 master，本仓库当前为 main，必须给出有效基线 |
| 前端自定义规范 | 在 frontend 执行 `python script/code_check.py -d src` | 是全量检查，遗留问题与本轮引入问题分别记录 |
| 接口与行为 | 有针对性的自动化回归或可重复的 API/浏览器开发自测 | 覆盖认证、权限、分享失效、容量和下载完整性 |

检查前确认工具依赖。原后端检查器使用 javalang，解析失败后打印警告并跳过文件；扫描目录和语法支持须核对。它默认不会因新增兄弟服务就自动覆盖全部服务。增量文件来自 Git diff，未跟踪新文件需另行列举检查或使用模块全量扫描。

不得把零退出码直接写成“全部新服务规范通过”。记录实际扫描范围、解析跳过和未执行项。规则文档与配置不一致时以实际工具行为核实，必要调整须说明理由，避免整目录豁免。

本轮新增自动化测试集中覆盖容易退化的鉴权、并发唯一性、分享失效与错误处理；简单样式、文档和机械替换通过相应静态检查验证。旧团队、回收站用例按课程范围核对，移除用例须说明对应功能已移出首版。

## 8. 阶段完成和 AB 交接

每个功能执行“确认范围和契约 → 实现 → 静态及构建检查 → 业务自测 → 同步文档和进度 → 审阅差异 → 单独提交 → 单独推送 → 下一功能”。每个功能都保留可追溯的提交和验证结果。遇到新故障先保留必要信息，修复后只补跑受影响检查，再推进下一步。

| 阶段 | 交付条件 |
|---|---|
| 认证 | 注册、登录、基础资料可用，真实 JWT 被 B 文件服务接受，错误和过期凭证被拒绝 |
| 个人文件前端 | 目录、上传、下载、重命名、永久删除和容量可用，页面不再调用已移出功能 |
| 分享 | 创建、列表、取消、公开与提取码下载可用，越权、过期和源文件失效按协议拒绝 |
| A 运行交付 | A 三个镜像可从源码构建，运行配置及健康接口齐备，前端按路径转发并拒绝内部接口 |
| AB 联调 | 两个用户与匿名访问完成正反向用例，下载 SHA-256 一致，记录问题与结论 |

AB 开发核验包含并发注册、文件归属、名称冲突、目录空删、上传失败与配额、重复删除、正确/错误提取码、重命名后的原分享、取消/过期/源文件删除和依赖暂不可用。记录样本、预期、实际、环境与源码版本。此类自测为开发交付依据，正式实验按既定分工执行。

原网盘代码通过 Git 保存，课程运行路径只加载选定服务。删除旧代码前先检查引用、组件扫描、配置和测试影响；实际启动验证后才认定旧依赖已解除。
